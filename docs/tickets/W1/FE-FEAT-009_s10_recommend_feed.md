## Problem

`/feed` 가 장소를 나열하지만 **왜 그 순서인지 알 수 없다.** 인기순도 거리순도 아닌데
화면에 아무 근거가 없어서, 사용자 입장에서는 임의의 목록과 구별되지 않는다.

이 서비스의 차별점이 "인기순이 아닌 내 유형 기준"인데, 그 기준이 화면에 없으면
차별점이 존재하지 않는 것과 같다.

부수적으로 날씨 바(`LiveStatusBar`)의 `맑음 27도 해운대` 가 코드에 박힌 값이고,
하단 탭이 존재하지 않는 화면(`/search`·`/saved`)을 가리킨다.

## Context

### 피그마는 기획서로 읽는다

가져오는 것은 **화면 목적**과 **반드시 있어야 하는 정보** 둘뿐이다. 레이아웃·컴포넌트·
상태·인터랙션은 이 티켓에서 설계한다. 다르게 간 곳은 아래 전용 절에 적는다.

목업 — `docs/_internal/concept_v5.html` · `tabs_screens.html`

| 용도 | 자료 |
|---|---|
| 화면 목적·요소 | 피그마 `S10 · 추천 피드`(`1081:524`) · 유나 목업(9/11) |
| 유형명·축 문구 | `src/data/cf8Profiles.ts` (시트 `2_03A_CF8프로필` 사본) |
| 근거 문장 | `placeTags.whyKo` |

### 데이터 채움률이 설계를 정한다 (2026-09-11 실측, n=49)

```
전건 있음    cf8Match · whyKo · weatherType · stayMinutes · budgetLevel
             crowdLevel · addr1 · localDepth

0/49         placeType           ← 카드 메타를 `지역 · 분류` 로 만들 수 없다
```

### 🔴 엔진이 날씨를 반영하지 못한다

`weather: "rainy"` 로 `rankPlaces` 를 돌린 실제 결과 상위 3곳이 **전부 야외**다.

```
1위 봉래산          outdoor  150분
2위 절영해안산책로   outdoor   90분
3위 송도해안볼레길   outdoor  120분
```

`situationalScore` 가 읽는 `weatherScoreRainy` 가 DB에 **키 자체로 없어** 보정이 0이다.
따라서 화면에 "비가 와서 실내부터 보여드려요" 류의 문구를 쓰면 **사실과 다르다.**

`weatherType`(indoor/outdoor/mixed)은 49/49 있으므로 대안은 있으나, 순위 계산식
변경은 엔진 영역(에린)이라 이 티켓에서 하지 않는다. 화면은 **반영되지 않았다는 사실에
맞는 문구**만 쓴다.

### 포함 — 저장 (S40)

`PlaceRow` 를 그대로 쓰되 **순번을 뺀다.** 순번은 "추천 순서" 라는 뜻인데
저장 목록은 내가 고른 것이라 순위가 없다.

**지역으로 묶지 않는다.** 타겟이 외국인이라 `Yeongdo` · `Jung-gu` 가 아무 의미가 없다.
평면 목록 · 최근 저장순이고, 지역은 행 안의 메타로 남는다.

빈 상태는 **예외가 아니라 첫 화면이다.** "무엇을 하면 채워지는지" 를 적고,
저장 기능을 보면 떠올리는 "로그인해야 하나" 도 여기서 답한다.

저장값 스키마를 바꾼다 — 지금은 배열 순서가 곧 저장순이지만 그건 계약이 아니라 우연이다.

```
전   ["1013694", "3083767"]
후   [{ id: "1013694", savedAt: "2026-09-13T07:12:00Z" }]
```

배포 전이라 마이그레이션은 넣지 않는다.

## Strategy

### Step 1: 취향 요약을 화면 맨 위에

유형명과 3축을 먼저 보여 "이 목록은 이 기준으로 골랐다"를 선언한다. 조건(S03)을
CUSTOM 으로 골랐으면 함께 요약한다. QUICK 이면 조건이 반영되지 않았으므로 표시하지
않는다 — 반영 안 된 것을 보여주면 반영된 것처럼 읽힌다.

### Step 2: 상황 줄은 사실만

기상청 실제 값만 쓴다. 날씨가 순위에 반영되지 않으므로 "비가 와서 실내부터" 같은
인과 문구를 쓰지 않고, 관측 사실과 결과 개수만 적는다.

### Step 3: 카드 — 근거를 제목 다음에

`whyKo` 가 이 화면의 핵심이라 제목 바로 아래 둔다. 메타(`지역 · 실내/실외 · 체류`)는
보조로 내린다. 이미지가 없는 5곳을 위해 자리를 고정하고 대체 표시를 둔다.

### Step 4: 상태 5종

로딩은 카드 형태 스켈레톤으로 — 목록이 생길 자리를 미리 알려준다.

### Step 5: 하단 탭 3개

없는 화면(`/search`·`/saved`)을 가리키던 탭을 걷어내고 `추천 · 저장 · 내 정보` 로 바꾼다.
`시작` 을 뺀 이유는 `docs/decisions/하단탭_3개_구성.md` 에 있다 — 진단을 마친 사람에게
S00 은 갈 이유가 없는 화면이다.

아이콘은 뜻이 겹치지 않게 나눈다.

```
나침반    추천      당신 기준으로 방향을 잡아준다
북마크    저장
사람      내 정보
핀        S20 의 지도 버튼 (이 한 지점)
접힌 지도  S33 루트 지도 모드 — 비워둔다
```

## Implementation Notes

(구현 후 작성)

### ⚠️ `placeType` 뱃지는 목업 데이터다

분류 뱃지가 **49곳 중 23곳**에만 붙는다. 그 23곳의 값도 정본이 아니다.

| 출처 | 건수 | 근거 |
|---|---|---|
| TourAPI `contentTypeId` | 14 | 38 쇼핑 → 시장형 · 14 문화시설 → 문화역사형 |
| 손으로 찍음 | 9 | **근거 없음.** 뱃지 4종을 화면에서 확인하려고 넣음 |
| 없음 | 26 | `contentTypeId=12`(관광지)에 시장·해변·전망대·산이 섞여 규칙으로 못 가름 |

`src/data/placeTypeDraft.ts` 한 파일에 격리했다. 정본이 생기면 그 파일을 지우고
`PlaceRow` 의 `?? draftPlaceType(place)` 만 떼면 된다.

**정본이 없는 이유는 태깅이 덜 돼서가 아니다.** `scripts/import-place-tags.ts:112`
가 `placeType: null` 을 하드코딩한다 — 주석에 `정본 시트에 없음(구 스키마 필드,
category와 값 불일치라 매핑 보류)`. 즉 **시트에 컬럼 자체가 없고**, 들어올 통로가
없다. 담당은 유나·태무(`docs/데이터_마트_정의서.md` 2번 섹션).

푸는 길이 셋인데, 2번이 가장 싸다 — 시트에 이미 값이 있으면 태깅 작업이 없어진다.

1. 시트에 `place_type` 컬럼을 새로 만들고 49건 태깅
2. 기존 `category` 컬럼 값을 4종으로 매핑 (먼저 distinct 값 확인 필요)
3. `placeType` 을 버리고 뱃지를 다른 축으로 (`weatherType` 은 지표 줄과 중복)

### 날씨는 화면 진입 시 1회만 조회한다

3단이 겹쳐 있다.

| 단계 | 주기 |
|---|---|
| 기상청 발표 | 하루 8회 (02·05·08·11·14·17·20·23시, +10분부터 조회 가능) |
| 예보 슬롯 | 1시간 |
| 앱의 조회 | **화면 진입 시 1회** (`useRecommendations` 의 `}, [])`) |

`/api/weather` 는 `cache: "no-store"` 라 캐시가 없다. 탭을 옮겼다 돌아오면 다시
마운트되어 재조회하므로 평소에는 최신으로 보인다.

**문제는 피드를 켜둔 채 한 시간 이상 두는 경우다.** 10:00 에 들어와 11:30 까지
같은 화면에 있으면 여전히 `10:00 기준` 이다. 앱이 `지금 이 순간` 을 파는데
화면의 "지금" 이 멈춰 있는 셈이다.

후속으로 둘 중 하나. `useRecommendations`(에린 파일)를 고쳐야 해 이 티켓에서는
하지 않았다.

1. `visibilitychange` 로 포그라운드 복귀 시 재조회 — 주머니에서 꺼내 보는 게 주
   사용 패턴이라 효과가 가장 크다
2. 다음 정시까지 타이머를 걸어 슬롯 경계에서 자동 갱신

### 화면은 `page` · `Content` · `Skeleton` 셋으로 나눈다

`page.tsx` 는 껍데기만 갖고(9 줄), 데이터를 쓰는 본문과 로딩 자리는 옆 파일로
뺐다. 페이지에서 `loading ? … : …` 이 사라진다.

```
feed/   page.tsx · FeedContent.tsx · FeedSkeleton.tsx
saved/  page.tsx · SavedContent.tsx · SavedSkeleton.tsx
me/     page.tsx · MeContent.tsx
```

`me` 만 스켈레톤이 없다. 네트워크가 없고 기다리는 것이 하이드레이션뿐이라,
화면 전체를 덮으면 이미 준비된 언어·소개 절까지 가린다. 불확실한 두 값만 덮는다.

나중에 React Query 가 들어오면 `page.tsx` 만 아래로 바뀌고 스켈레톤 파일은
그대로 쓴다. `Suspense` 는 서스펜드하는 것이 있어야 작동하는데, 지금 데이터는
`useEffect` + `setState`(추천·날씨)와 동기 `localStorage`(유형·저장)뿐이라
둘 다 서스펜드하지 않는다.

```tsx
<Suspense fallback={<FeedSkeleton />}><FeedContent /></Suspense>
```

**남는 비용** — 본문과 스켈레톤이 "어떤 블록이 어떤 순서로 오는가" 를 각자 안다.
피드에 블록을 더해도 스켈레톤이 안 따라오면 **타입 에러도 테스트 실패도 나지
않는다.** 마크업 복제는 `ScreenTitle`·`SectionHeader` 로 뽑아 없앴지만 배치까지는
못 없앤다(슬롯을 받는 레이아웃 컴포넌트가 필요한데, 삼항식이 슬롯 자리로 옮겨갈
뿐이라 득이 없다). 두 파일을 같은 폴더에 나란히 둔 것이 완화책이다.

### 정렬 UI 는 선택지 수가 정한다

추천 탭의 `추천순` 은 지금 **텍스트 한 줄**이다. 고를 것이 하나뿐이라 컨트롤로
만들면 열어도 바꿀 게 없어 고장으로 읽힌다.

선택지가 늘면 이렇게 간다.

| 선택지 | 컨트롤 | 지금 쓰는 곳 |
|---|---|---|
| 1개 | 텍스트 | 추천 탭 |
| 2~3개 | 세그먼트 | 저장 탭(최근 저장순·적합도순) |
| 4개 이상 | 드롭다운 | 없음 |

추천 탭이 드롭다운으로 갈 때 저장 탭도 따라갈지는 그때 정한다. 탭마다 정렬 UI
가 다르면 같은 동작을 두 번 배우게 되므로, **둘 다 드롭다운으로 맞추는 쪽**이
기본값이다.

막고 있는 것은 컨트롤이 아니라 **기준이 될 데이터**다. 거리순은 좌표를 서버로
보내지 않기로 했고(부산 고정), 인기순은 저장 수가 없고, `지금 영업중` 은 영업시간
필드가 없다. 하나라도 생기면 그때 컨트롤을 올린다.

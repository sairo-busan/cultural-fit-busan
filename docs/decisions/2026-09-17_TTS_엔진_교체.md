# TTS 엔진 교체 검토 (9/17)

## 문제

BE-FEAT-017·018에서 도슨트 음성(한글 240개 + 영문 238개, 총 478개)을
`edge-tts`(Microsoft Edge 브라우저의 TTS 기능을 역엔지니어링한 **비공식**
클라이언트)로 만들었다. 공식 API가 아니라 공모전 제출작에 써도 되는지
이용조건이 불명확하다(소피 발견, PR #49 리뷰).

## 실제 분량 확인

한글+영문 간단히·자세히 4종 합계(120곳 기준, `place_info` 실측):

| 필드 | 글자수 |
|---|---|
| 간단히 Ko | 23,731 |
| 자세히 Ko | 103,561 |
| 간단히 En | 61,433 |
| 자세히 En | 252,822 |
| **합계** | **441,547** |

## 검토한 대안

| 방식 | 무료 한도 | 441,547자 대비 | 한국어 지원 |
|---|---|---|---|
| **Azure Speech(F0)** | 월 500,000자(뉴럴, 만료 없음) | 88% 소진 — 재작업·재생성 여유 거의 없음 | 공식, ko-KR 뉴럴 다수 |
| **Google Cloud TTS** | 월 1,000,000자(Standard/Neural2) | 44% 소진 — 여유 충분 | 공식, ko-KR Standard/Neural2 |
| **Piper**(로컬 오픈소스) | 무제한(로컬 실행) | 해당 없음 | **비공식/커뮤니티 모델 의존** — 공식 배포판에 한국어가 일관되게 포함 안 됨(문서마다 다름), HuggingFace의 `neurlang/piper-onnx-kss-korean` 같은 커뮤니티 모델을 써야 할 수 있음. 품질·라이선스 재확인 필요, 로컬 Python 셋업 시간 소요 |
| **Kokoro**(로컬 오픈소스) | 무제한(로컬 실행) | 해당 없음 | **한국어 지원 불명확** — 공식 v1.0 릴리스는 8개 언어(영어 2종·es·fr·hi·it·ja·pt-BR·zh)만 지원, 한국어 없음. 일부 홍보성 사이트는 한국어 지원을 주장하나 근거 불명, GitHub에 "한국어 지원해달라"는 이슈(#294)가 열려있어 신뢰 불가 |

## 결론 — Google Cloud TTS 추천

- Azure는 무료 한도 88% 소진이라 재생성·수정 여유가 거의 없음(제출 전까지
  원고 수정 가능성 있음을 고려하면 리스크)
- Piper·Kokoro는 한국어 지원 자체가 불확실 — 마감(9/21) 임박한 상황에서
  검증에 시간 쓰는 것도 리스크
- Google Cloud TTS는 한도 여유(44%)·공식 API·한국어 공식 지원 셋 다
  만족하는 유일한 선택지

## 막힌 것 — 사용자 액션 필요

Google Cloud 프로젝트 생성 + Text-to-Speech API 활성화 + 서비스 계정 키
발급은 사용자의 Google 계정 로그인이 필요해 Claude Code가 대신 할 수 없다.

**요청**:
1. https://console.cloud.google.com 에서 프로젝트 생성(또는 기존 프로젝트 사용)
2. "Cloud Text-to-Speech API" 활성화
3. 서비스 계정 생성 → JSON 키 발급
4. 키 파일을 안전하게 전달(예: `.env.local`에 키 경로 또는 내용 추가)

키를 받으면:
1. `generate-docent-audio-ko.ts`/`generate-docent-audio-en.ts`를 Google
   Cloud TTS SDK(`@google-cloud/text-to-speech`) 기반으로 다시 작성
   (ko-KR/en-US Standard 또는 Neural2 보이스로 SunHi·Jenny와 톤 비슷한 것 선정)
2. 기존 edge-tts 478개 mp3 전량 재생성(문장별 타임스탬프 포함 — 아래 참고)
3. `addRandomSuffix: true`로 이미 고친 업로드 스크립트로 재업로드
4. `place_info`의 `audioUrl*` 필드 값 갱신(같은 필드, URL만 바뀜) +
   `audioMarks*` 신규 필드 추가 — `placeDetail.ts` 응답 변경 있음(아래 참고)

## 추가 요구사항(9/18, 소피) — 문장별 재생 시각(audioMarks)

도슨트 화면에서 지금 읽는 문장을 하이라이트하려고 문장별 시작 시각이 필요.
필드명 `audioMarks{Simple,Detail}{Ko,En}`, 형태
`[{ startSec, text }, …]`(문단 아니라 **문장** 단위, 번호 대신 원문 텍스트를
같이 내려서 소피 쪽에서 원고를 다시 나눌 필요 없게).

### SSML `<mark>` + timepoints는 쓰지 않는다

Google Cloud TTS가 `enableTimePointing: ["SSML_MARK"]`로 이 기능 자체는
제공하지만(v1beta1), 확인해보니 신뢰하기 어렵다:
- **Neural2 보이스에서 timepoints가 아예 안 돌아오는 알려진 버그**가
  Google 이슈 트래커에 있음(issuetracker.google.com/issues/243702062)
- v1beta1(베타) 전용 — 정식(GA) v1 API엔 없음
- "연속된 mark 사이에 오디오가 없으면 이벤트가 안 생긴다" 등 제약도 있어
  문장이 짧으면 씹힐 위험

### 대안 — 문장별 개별 합성 + 실측 길이로 조립 (채택)

1. 원고를 문장 단위로 분리(한국어/영어 문장부호 기준 규칙 분리)
2. **문장마다 따로** TTS 요청 → `LINEAR16`(wav)로 받는다(mp3 아님 —
   아래 참고, 표준 v1 API만 사용, beta 불필요)
3. 각 wav 클립의 실제 재생 길이를 계산(헤더의 샘플 수/샘플레이트로 정확히
   계산 가능 — 인코더 여백이 없는 raw PCM이라 근사치가 아니라 정확한 값)
4. 누적 합산으로 `startSec` 계산(문장0=0, 문장1=문장0 길이, …) — **실측
   기반이라 SSML timepoint보다 오히려 더 정확**. 문단이 바뀌는 지점은
   짧은 무음을 끼워 자연스럽게 쉬게 한다
5. wav 클립들을 `ffmpeg`(로컬 설치 확인됨, `/opt/homebrew/bin/ffmpeg`)로
   먼저 이어붙인 뒤, **그 결과물 하나만** mp3로 인코딩(소피 리뷰 — mp3는
   클립마다 인코더 여백이 붙어서 문장 단위로 이어붙이면 수십 ms씩 밀려
   끝에서 최대 1초 가까이 어긋날 수 있음. wav로 이어붙이고 마지막에 한 번만
   인코딩하면 이 문제가 없음)
6. `text`는 원고에서 **그대로 잘라낸 부분 문자열**로 넣는다 — 공백·따옴표·
   줄바꿈을 다듬지 않는다(소피 리뷰 — 화면이 원고 안에서 `text`를 찾아
   그 문장만 굵게 표시하므로, 정규화하면 못 찾음)
7. `audioMarks*`에 `{ startSec, text }` 배열로 저장, `place_info`에 추가
   필드로 얹어 `placeDetail.ts` 응답에 반영

총 글자수는 문장 단위로 쪼개도 동일(요청 횟수만 늘어남, Google Cloud TTS는
글자수 기준 과금이라 비용 영향 없음). GCP 키 받으면 이 설계로 바로 구현.

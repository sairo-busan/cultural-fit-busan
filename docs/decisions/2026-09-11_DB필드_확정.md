# DB 필드·데이터 소스 확정 (2026-09-11)

추천엔진 고도화를 위해 실제 데이터 소스를 정리하고, 유나가 신설한 DB 탭(DB_01~03)에 어떤 필드를 더 넣을지 결정한 기록. 에린 작업 세션 결과이며, 유나·태무·소피 확인이 필요한 항목은 맨 아래에 모아 둔다.

## 배경

- 9/10 회의에서 스코어링 모델이 바뀌었고(6분할 컬럼 합산), 조건값은 점수화하지 않고 필터로만 쓰기로 정리됨.
- 유나가 구글시트에 `DB_리스트`(컬럼사전), `DB_01 점수판`, `DB_02 장소정보`, `DB_03 CF8별 장소추천사유` 4개 탭을 신설.
- 에린은 이제 `01_FINAL`·`placeTags` 컬렉션을 쓰지 않고, **구글시트 DB 3개 + TourAPI 정본 `places` 컬렉션** 만으로 엔진을 다시 붙인다.

## 확정 데이터 모델

원천은 4개다.

| 소스 | 키 | 담는 것 | 쓰이는 시점 |
|---|---|---|---|
| `places` (MongoDB, TourAPI 정본) | content_id | mapx·mapy, 주소, 대표이미지 URL, 이름, 운영시간·휴무일, 무장애 정보 | S10 이미지·좌표, 근처 장소, S20 상세 |
| `DB_01 점수판` | place_id | 점수 24컬럼 + 대표 content_id + (신규) `indoor_outdoor` | 엔진이 랭킹 계산 시 항상 로드 |
| `DB_02 장소정보` | place_id | `place_desc` (S10 카드 한 줄) | S10 카드 표시 |
| `DB_03 CF8별 장소추천사유` | (CF8_CD, place_id) | `recommendation_reason` | S20 상세에서 유형별 추천 이유 |

- 조인 체인: `DB_01.content_id` = `places.content_id` (장소당 대표 콘텐츠 1개, 실질 1:1).
- `placeTags` 컬렉션은 폐기. import 스크립트는 탭별로 하나씩 3개 새로 작성한다.
- 리스트 경로에서 필요한 것은 `DB_01` + `DB_03` + `places`. `DB_02`는 카드 텍스트 hydrate 용도.

### content_id 위치

- 별도 매핑 테이블을 만들지 않는다. `DB_01`의 `대표컨텐츠ID` 컬럼을 그대로 쓴다.
- 이유: 120행에 스칼라 하나 때문에 컬렉션을 늘릴 이득이 없다. import 때 place_id 기준 한 문서로 병합하고, API는 `places.find({ content_id: { $in: [...] } })` 한 번으로 조인한다. 조인 비용은 무시 가능(밀리초).
- `DB_02`·`DB_03`에는 content_id를 넣지 않는다. 둘 다 place_id로 조인한다.
- 나중에 상세 화면에서 "한 장소 안의 여러 콘텐츠"가 필요해지면 그때 매핑 탭을 신설한다.
- 현재 `DB_01` 대표컨텐츠ID는 119/120만 채워져 있다(1곳 공란).

## 하드필터 재검토

점수 계산은 `DB_01`의 기존 24컬럼(CF 6 + 동행 5 + 날씨 3 + 계절 4 + 시간 3)만 사용한다. 나머지는 전부 후보에서 빼는 필터이며 점수를 매기지 않는다.

처음에 검토한 하드필터 11종을 아래처럼 정리했다.

| 항목 | 결정 | 근거 |
|---|---|---|
| `indoor_outdoor` (INDOOR/OUTDOOR/MIXED) | **DB_01에 신설** | 유저가 "실내 우선"을 선택함(프론트 `currentSituation`에 이미 존재). 비 올 때도 참고. 태깅 난이도 낮음 |
| `is_restaurant` | TourAPI `contenttypeid=39` / `lclsSystm1=FD`로 자동 파생. 유나는 예외만 오버라이드(선택적 컬럼) | "식사 전"이 아니면 식당을 후보에서 제외 |
| 보행부담 세부 4종(휠체어·계단·유모차·경사) | **DB 컬럼 안 만듦.** 무장애 여행 API를 배치로 긁어 `places`에 저장 → "이동약자 배려시설 있음" boolean 1개로 파생 | API 필드가 세부 4종과 1:1로 맞지 않고, 데이터도 대부분 공란이라 세분화 의미 없음 |
| `pet_allowed` | **[9/11 수정] DB_01에 신설.** 반려동물 동반 전용 API로 우리 content_id 120곳 대조한 실측 결과 커버리지 15%(18곳)뿐 — API 단독 불가로 판정 뒤집힘. API가 확인한 18곳을 시드값으로 채우고, 나머지 102곳은 유나가 조사·추측으로 보완(9/10 회의 원안대로 복귀) | 실측 전엔 "1곳뿐"이라는 속성사전 구값을 근거로 컬럼 자체를 안 만들기로 했었는데, content_id 기준 재확인 결과 18곳으로 나와 판단 변경 |
| `barrier_free` | **DB 컬럼 안 만듦.** 무장애 여행 API(커버리지 66.7%)로만 파생, `places`에 저장 | API 단독으로 쓸 만한 수준이라 수작업 보완 불필요 |
| 음식 하드필터(날것·비건·해산물·돼지고기) | **DB 컬럼 안 만듦.** 이번 범위에서 빼는 쪽으로 제안(팀 확인 필요) | 식당이 소수이고 공식 메뉴를 120곳 검증하는 부담이 큼. 틀리면 신뢰 문제. 프론트/피그마 S03엔 아직 질문이 남아 있어 조율 필요 |

**null/false 설계 원칙(9/11 소피 교차확인)**: `pet_allowed`·`barrier_free` 둘 다 "확인된 false"와 "미등록(null)"을 구분한다. 미등록을 false로 채우면 필터 선택 시 대부분이 사라짐(실측: 휠체어 선택 시 120곳 중 40곳 미등록으로 사라짐, 반려동물 선택 시 102곳 사라져 18곳만 남음) — `hardFilter.ts`가 원래 접근성 필드에 쓰던 원칙(03A-4 `HF_WHEELCHAIR`: 확인된 false만 제외, null은 통과 + "정보 확인 중" 표시)을 그대로 따른다. 두 API 모두 "명시적 불가" 신호를 거의 안 주므로 실무적으로는 `true`/`null`로만 채워지고 `false`는 드물다.
| `service_active` (운영 여부) | **DB 컬럼 안 만듦** | 폐업/휴관 관리를 팀이 계속할 수 없음. TourAPI에서 폐업하면 목록에서 빠지므로 추천에서도 자동 제외됨. 유나 큐레이션 120곳은 운영 중 전제 |

결과적으로 `DB_01`에 새로 추가하는 컬럼은 `indoor_outdoor`와 `pet_allowed` 둘이며(선택적으로 `is_restaurant` 오버라이드), 나머지는 원래 시트에 없던 것을 추가하지 않는 것이다.

## 무장애 여행 정보 — API 조사 결과

- 서비스: 한국관광공사 `KorWithService2`. 상세 오퍼레이션 `detailWithTour2` (contentId 단위).
- 부산 등록 386건. 반환 필드 약 30개: `wheelchair`(휠체어 대여), `exit`(출입구 경사/턱), `elevator`, `restroom`(장애인 화장실), `parking`(장애인 주차), `route`(이동 경로), `stroller`(유아차 대여), `braileblock`(점자블록), `helpdog`, `audioguide`, `lactationroom`(수유실), `babysparechair` 등.
- 값은 모두 자유 텍스트("대여가능", "주출입구 경사로가 있어 휠체어 접근 가능함", 빈 문자열 등). y/n 아님.
- 커버리지 편차가 크다(해운대해수욕장은 풍부, 소규모 장소는 대부분 공란).

활용 — **원본과 파생값을 같은 `places` 문서에 함께 저장한다**(파생값만 남기고 원본을 버리지 않음):

```ts
// scripts/ingest-places.ts — fetchDetail()에 추가
const withTour = await callTourApi("detailWithTour2", { contentId }).catch(() => null);
const accessibilityInfo = withTour?.items?.item?.[0] ?? null;  // ~30개 필드 원본 그대로

const barrierFree = accessibilityInfo
  ? Object.values(accessibilityInfo).some((v) => typeof v === "string" && v.trim() !== "")
  : null;  // API에 이 장소 자체가 없음 = UNKNOWN(null). "조사된 게 없다"는 뜻이 아니라 API 미등록
```

- `places.accessibilityInfo`: `detailWithTour2` 응답 원본(`wheelchair`·`exit`·`elevator`·`restroom`·`parking`·`route`·`stroller`·`braileblock`·`helpdog`·`audioguide`·`lactationroom`·`babysparechair` 등). S20 상세 화면이 여기서 값이 있는 필드만 골라 문장으로 나열한다("휠체어 대여 가능", "장애인 화장실 있음" 등, 빈 문자열은 스킵).
- `places.barrierFree`: `true | null` — "이동약자 배려시설 있음" 여부 하나로 파생. `hardFilter.ts`는 이 필드만 보고 필터링한다(S03 보행부담 4개 선택 모두 이 boolean 하나를 참조). `false`는 API가 명시적 불가 신호를 거의 안 줘서 실무적으로 거의 안 나온다.

## 반려동물 동반 — API 조사 결과

- 서비스: 한국관광공사 `KorPetTourService2`. `areaBasedList2`로 부산 653건 목록 확인.
- 우리 대표 content_id가 이 목록에 포함되는지 대조해 `pet_allowed`를 파생한다. 상세 오퍼레이션(`detailPetTour2`)은 커버리지가 낮아 목록 포함 여부만 사용.

## 운영시간·휴무일

- TourAPI에 "폐업" 플래그는 없다(`showflag` 없음). `areaBasedList2`/`detailCommon2` 어디에도 없음.
- `detailIntro2`에 `usetime`(운영시간), `restdate`(휴무일)가 자유 텍스트로 존재.
- 이 두 필드를 `places`에 저장해 두되 이번 범위에서는 로직에 반영하지 않는다. 나중에 "지금 영업 중" 기능에서 파싱해 쓴다.

## 이미지 — 방식 B 확정 (실측 완료)

- S10 카드 이미지는 배치 시 `places`에 저장한 `firstImage`/`firstImage2` URL을 그대로 `<img src>`로 쓴다. 브라우저가 관광공사 CDN(`tong.visitkorea.or.kr`)에서 직접 로드.
- 실측(로컬, 5회): 썸네일 약 50KB, 총 소요 약 0.10초. 원본 약 83KB, 총 약 0.14초. DNS·연결 포함.
- S10에서 7장을 병렬로 불러도 1초 안. 실시간 TourAPI 재호출(방식 A)은 불필요.
- `ingest-places.ts`는 이미 `firstImage`·`firstImage2`·`images[]`를 저장하고 있어 추가 작업 없음.
- `DB_01`·`DB_02`에 이미지 URL 컬럼은 넣지 않는다. `firstImage`가 빈 장소용 플레이스홀더 1장만 준비.

### 배치 vs 실시간 요약

- 무장애·반려·이미지·좌표·운영정보는 전부 **배치**(`ingest-places.ts` 1회 실행)로 `places`에 적재한다. 앱 런타임에는 호출하지 않는다.
- 런타임에는 저장된 값만 읽으므로 추천 응답 속도에 영향이 없다.
- 운영시간·휴무일처럼 자주 바뀌는 정보만 이후 주기적으로 재적재한다.

## 화면별 필드 매핑

| 화면 | 소스 | 내려주는 필드 |
|---|---|---|
| S10 피드(유형별 점수 랭킹 7개) | 스코어링 `DB_01` / 카드 `DB_02` + `places` | 이미지(`places.firstImage`), 장소명(`DB_02`), 장소설명(`DB_02.place_desc`) |
| S20 상세(카드 탭) | `DB_03` + `places` | 유형별 추천 이유(`DB_03`), 무장애 raw 텍스트(`places`) |

동선:
1. 엔진이 `DB_01`만으로 랭킹 → place_id 7개 확정
2. 7개 → `DB_02` place_id 조인 → 장소명·설명
3. 7개의 content_id(이미 `DB_01`에서 확보) → `places` 조인 → 이미지·좌표
4. 카드 탭 → (유저 CF8 코드 + place_id)로 `DB_03` 조회 → S20 추천 이유
5. `whyKo`는 `DB_03`이 대체한다.

- `ingest-places.ts` 확장: `detailWithTour2`(무장애) 호출 추가, `KorPetTourService2` 목록 대조 추가 → `places`에 저장.
- import 스크립트 신규 3개: `DB_01`(score_board), `DB_02`(place_info), `DB_03`(place_by_cf8). `import-place-tags.ts`·`import-place-scores.ts` 폐기.

  - `cf8Match.ts` → 6분할 컬럼 중 유저 코드에 해당하는 3개를 합산하는 모델로 교체

  - `hardFilter.ts` → `indoor_outdoor`·`is_restaurant`·무장애 boolean·`pet_allowed`·현재상황 필터

## 팀 확인 대기

유나·태무:
1. 음식 제약 — 피그마 S03과 프론트에 아직 질문이 남아 있음. 빼는 쪽으로 정리할지, 유지한다면 데이터를 어떻게 채울지.
2. `DB_01`에 `indoor_outdoor` 컬럼 추가 후 120곳 태깅(INDOOR/OUTDOOR/MIXED).
3. `DB_01`에 `pet_allowed` 컬럼 추가. 에린이 API로 확인한 18곳(Y) 시드값 전달 예정 — 나머지 102곳은 유나가 조사·추측으로 Y/N/UNKNOWN 채움.
4. `DB_01` 대표컨텐츠ID 공란 1곳.
5. `DB_02` `place_desc` 120건(30자 기준).
6. `DB_03` `recommendation_reason` 960건(8유형 × 120곳).

소피:
- 음식 제약을 빼기로 하면 S03 화면에서 해당 섹션 제거.
- `useRecommendations` 훅이 날씨를 반환하도록 바뀌면 `LiveStatusBar` 연결.

## 미해결·후속

- 무장애 raw 텍스트를 boolean으로 환산하는 규칙(값이 있으면 지원, 공란이면 UNKNOWN, 명시적 불가 표현 처리)은 구현하며 확정.
- 다국어(영·일·중): `DB_02`·`DB_03`에 언어별 컬럼이 필요하지만, 어떤 언어를 지원할지는 유나·태무 논의 후 전달 예정.
- 계절·시간대 경계, 점수 스케일 정규화는 에린이 정한다.

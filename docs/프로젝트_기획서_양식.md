# 프로젝트 기획서 최소 양식

> 코드베이스를 읽혀서 자동 생성할 수 있는, 프로젝트 수행에 필요한 최소한의 문서 체계
>
> 분석 원본: SAIRO(Cultural Fit Busan) + 인톡 파트너스 + 신한 PoC | 2026-08-13

---

## 문서 구조 요약

| Tier | 문서 | 파일 | 코드에서 추출 가능 |
|------|------|------|--------------------|
| **1 · 필수** | 프로젝트 컨텍스트 | `CLAUDE.md` | ✅ |
| **1 · 필수** | 도메인 모델 정의서 | `docs/도메인모델.md` | ✅ |
| **1 · 필수** | 화면 IA | `docs/화면_IA.md` | ✅ |
| **2 · 권장** | 유저플로우 | `docs/유저플로우.md` | ✅ |
| **2 · 권장** | WBS / 작업 분해 | `CLAUDE.md` 인라인 또는 Notion DB | △ (git log 역추론) |
| 3 · 선택 | 기술 결정 기록 (ADR) | `docs/decisions/` | ✅ |
| 3 · 선택 | 기능 상세 기획서 | `docs/features/` | △ |

- **Tier 1**: 없으면 개발 착수 불가
- **Tier 2**: 없으면 병목·재작업 발생
- **Tier 3**: 규모가 클 때 추가

## 문서 1. 프로젝트 컨텍스트

> 파일: `CLAUDE.md`  
> AI와 협업하든, 새 팀원이 합류하든, 가장 먼저 읽는 문서

```markdown
# {프로젝트 이름}

{누구를 위한 어떤 서비스인지 — 1줄}

## 기술스택

- 프레임워크: {Next.js 16 App Router 등}
- DB: {Supabase / Prisma 등}
- 배포: {Vercel / AWS 등}
- 외부 API: {사용 중인 외부 서비스}

## 팀 구성

- {이름}: {역할}

## 핵심 차별점

{이 프로젝트만의 고유한 가치 — 1~2문장}

## 주요 문서

- `docs/도메인모델.md` — {핵심 비즈니스 로직}
- `docs/화면_IA.md` — {전체 화면 구조}
- `docs/유저플로우.md` — {기능별 순서도}

## 현재 작업 순서

1. **FEAT-001** {설명} ← 현재
2. **FEAT-002** {설명}
3. ...

## 코드 규칙

- 커밋: `feat:`, `fix:`, `chore:` (한국어 본문)
- {기타 컨벤션}
```

**코드에서 추출 포인트**: package.json, tsconfig, 디렉토리 구조, .env.example, git log

## 문서 2. 도메인 모델 정의서

> 파일: `docs/도메인모델.md`  
> 서비스의 핵심 비즈니스 개념·분류·로직 정의

```markdown
# {도메인명} — {개념 이름}

{프로젝트명} / {날짜} / v1.0

## 1. 개념

{핵심 도메인 개념을 1~2문단으로}

## 2. 분류 체계

{축/카테고리/상태 등 핵심 분류}

| 코드 | 이름 | 설명 | DB 컬럼 |
|------|------|------|---------|
| ... | ... | ... | ... |

## 3. 상태 전이 / 계산 로직

{상태가 어떻게 변하는지, 점수 계산 산식 등}

## 4. 화면 표시 규칙

{각 화면에서 이 도메인을 어떻게 보여주는지}

| 화면 | 표시 |
|------|------|
| S02 | `CFP-QLMS · 조용한 골목 산책자` |
| S10 | 유형명만 |

## 5. DB 스키마 영향

{이 도메인이 요구하는 테이블/컬럼 목록}
```

**코드에서 추출 포인트**: Prisma schema, 타입 정의 파일, enum, 유틸 함수(점수 계산·상태 전이), seed 데이터

## 문서 3. 화면 IA

> 파일: `docs/화면_IA.md`  
> 전체 화면을 한 눈에 조망하는 표  
> 화면ID를 부여하면 "그 화면"이 아니라 "S20"으로 특정 가능

```markdown
# 화면 IA — {프로젝트명}

| 화면ID | 화면명 | 기능 | 화면목적 | 진입경로 | 이탈경로 | 비고 |
|--------|--------|------|----------|----------|----------|------|
| S00 | 랜딩 | - | 소개 | 직접 URL | - | |
| S01 | 온보딩 | F1 | 사용자 설정 | S00 시작하기 | S02 | |
| S10 | 메인 피드 | F2 | 핵심 콘텐츠 | S01 완료 | S20 | |
| S20 | 상세 | F3 | 판단 지원 | S10 카드 | S10 | 허브 화면 |
| S90 | 예외 4종 | - | 이탈 방지 | 전역 | 직전 | 로딩·0건·오류·권한 |
```

**코드에서 추출 포인트**: App Router `app/` 디렉토리(page.tsx, layout.tsx), 라우트 그룹, 미들웨어

## 문서 4. 유저플로우

> 파일: `docs/유저플로우.md`  
> 기능 단위로 사용자 경로를 순서도로 표현  
> 화면 IA가 "어떤 화면이 있는가"라면, 유저플로우는 "화면 사이를 어떻게 움직이는가"

```markdown
# 유저플로우 — {프로젝트명}

## F1. {기능명} (예: 온보딩)

​```
[시작] → S00 랜딩
         ↓ "시작하기"
       S01 온보딩
         ↓ 문항 응답
       ◇ 건너뛰기?
       ├─ Yes → 프리셋 선택 → S02
       └─ No  → 4문항 완료 → S02 결과
                              ↓
                            S10 피드
​```

## F2. {기능명} (예: 검색/탐색)

​```
S10 피드 → 카드 탭 → S20 상세
            ↓ 필터
          S11 검색 → 결과 → S20
​```
```

**코드에서 추출 포인트**: Link/router.push/redirect 호출, 폼 submit 후 이동, 조건부 렌더링 분기

> 복잡한 프로젝트는 mermaid 또는 SVG 순서도로 시각화 (SAIRO처럼 HTML로 만들어도 됨)

## 문서 5. WBS / 작업 분해

> 위치: `CLAUDE.md` 내 인라인 (소규모) 또는 Notion DB (팀 프로젝트)  
> 기능을 티켓 단위로 쪼개고 순서를 정함

### 인라인 버전 (소규모 프로젝트)

```markdown
## 현재 작업 순서

1. **FEAT-001** 앱 생성 + 배포 ← 현재
2. **FEAT-002** DB 연결 + API 라우트
3. **FEAT-003** 외부 API 연동
4. **FEAT-004** DB 스키마 설계
```

### 주차별 버전 (팀 프로젝트)

```markdown
| Phase | 주차 | 범위 | 상태 |
|-------|------|------|------|
| P0 기반 | W1-2 | 인프라 + 인증 | ✅ |
| P1 MVP | W3-6 | 핵심 기능 | 🔄 |
| P2 확장 | W7-9 | 부가 기능 | ⏳ |
| P3 안정화 | W10-11 | QA + 버그 | ⏳ |
```

**코드에서 추출 포인트**: git log의 feat 커밋, 브랜치명, PR 제목, 빈 페이지(placeholder), TODO 주석

## 다른 프로젝트에 적용하는 순서

1. **코드베이스 스캔** → package.json, 디렉토리 구조, schema, .env.example, git log 읽기 → **CLAUDE.md** 생성
2. **도메인 추출** → 타입 정의, enum, 상태 관리 로직, seed 분석 → **도메인 모델 정의서**
3. **화면 구조 파악** → app/ 디렉토리 page.tsx, layout.tsx 스캔 → **화면 IA**
4. **흐름 추적** → Link/router.push/redirect 추적 → **유저플로우**
5. **작업 역추론** → git log feat 커밋, 빈 페이지, TODO → **WBS 현황**

> **핵심**: 문서 간 ID를 통일하면 추적성이 확보됩니다.
> 화면 IA의 "S20"이 유저플로우에서도 "S20"이고, WBS에서도 "S20 관련 FEAT-012"로 연결됩니다.

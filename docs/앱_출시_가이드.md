## 1. 웹과 앱은 API 를 부르는 방식이 다르다

```
웹 (Vercel)
┌──────────────────────────────┐
│  화면          API           │   화면과 API 가 같은 주소에 있다
│  /feed   ──▶  /api/recommend │   → fetch("/api/recommend") 가 통한다
└──────────────────────────────┘

앱 (Capacitor)
┌────────────────┐                 ┌──────────────────────────┐
│  폰 안          │                 │  Vercel                  │
│  화면만 들어감   │  ── 인터넷 ──▶  │  /api/recommend          │
│  /api 는 없음   │                 │  (DB · API 키는 여기에만) │
└────────────────┘                 └──────────────────────────┘
```

앱은 **화면만** 폰에 들어가고, API 는 지금처럼 Vercel 에 남는다.
API 를 앱에 같이 넣지 않는 이유는 `MONGODB_URI` · `KMA_API_KEY` · `TOUR_API_KEY` 가 앱 파일에 들어가
누구나 꺼내볼 수 있게 되기 때문이다.

## 2. `apiUrl()` — 화면에서 API 를 부를 때

### 무엇인가

`src/lib/apiBase.ts` 에 있는 한 줄짜리 함수다. 경로 앞에 서버 주소를 붙인다.

```ts
const API_BASE = process.env.NEXT_PUBLIC_API_BASE ?? "";
export function apiUrl(path: string) {
  return `${API_BASE}${path}`;
}
```

| 빌드 | `NEXT_PUBLIC_API_BASE` | `apiUrl("/api/recommend")` 결과 |
|---|---|---|
| 웹 (Vercel) | 비어 있음 | `/api/recommend` — 지금과 동일 |
| 앱 | `https://cultural-fit-busan.vercel.app` | `https://cultural-fit-busan.vercel.app/api/recommend` |

웹 동작은 바뀌지 않는다. 앱 빌드 스크립트만 이 값을 채운다.

### 왜 필요한가

앱에서 `fetch("/api/recommend")` 는 **폰 안의** `/api/recommend` 를 찾는다. 거기엔 아무것도 없어서
요청이 실패하고 목록이 비어 보인다. **웹에서는 멀쩡해서** 브라우저로 확인해선 알 수 없다.

### 어떻게 쓰나

```diff
+ import { apiUrl } from "@/lib/apiBase";

- fetch("/api/recommend?limit=120")
+ fetch(apiUrl("/api/recommend?limit=120"))
```

| 적용 대상 | 해당 여부 |
|---|---|
| 화면(`"use client"` 컴포넌트 · 훅)에서 `/api/…` 를 부르는 `fetch` | ✅ 감싼다 |
| API 라우트(`src/app/api/**`) 안의 코드 | ❌ 해당 없음 |
| 서버에서 외부 API(기상청 · TourAPI)를 부르는 코드 | ❌ 해당 없음 |

현재 적용된 곳은 세 곳이다 — `useRecommendations.ts` 2곳 · `SavedContent.tsx` 1곳.

### 빠진 곳 찾기

```bash
grep -rn -E 'fetch\(\s*["`]/api' src --exclude-dir=api
```

결과가 비어 있어야 한다.

## 3. CORS — 서버 설정 한 곳에서 연다 *(확인 중)*

앱의 주소(`https://localhost`)와 API 주소(`cultural-fit-busan.vercel.app`)가 달라서, 서버가
"다른 주소에서 온 요청도 받는다" 는 헤더를 보내야 앱이 응답을 읽을 수 있다.

`next.config.ts` 에서 `/api/*` 전체에 한 번에 건다.

```ts
async headers() {
  return [{
    source: "/api/:path*",
    headers: [
      { key: "Access-Control-Allow-Origin", value: "*" },
      { key: "Access-Control-Allow-Methods", value: "GET, OPTIONS" },
    ],
  }];
}
```

- API 라우트 파일은 **건드리지 않는다**
- 새로 만드는 API 도 **자동으로** 적용된다
- 인증 · 쿠키가 없는 공개 조회 API 라 `*` 로 연다. API 키는 서버에만 있어 노출되지 않는다
- 누구나 우리 API 로 공공데이터 호출량을 쓸 수 있는 점은 남는다 — 호출량 제한은 제출 후 검토

## 4. 앱 업로드부터 심사 종료까지 API 응답 규칙

웹은 배포하면 화면과 API 가 함께 바뀐다. 앱은 **폰에 설치된 예전 화면이 새 API 를 부른다.**

```
            배포 전                         배포 후
웹     화면 v1 ─ API v1             화면 v2 ─ API v2     ✅ 같이 바뀜
앱     화면 v1 ─ API v1             화면 v1 ─ API v2     ⚠️ 앱은 업데이트 전까지 v1
```

필드가 빠지면 **심사위원 폰에서 목록이 뜨지 않는다.** 앱을 고치려면 원스토어 재심사를 거쳐야 해서 바로 복구할 수 없다.

| 변경 | 설치된 앱 | 업로드 ~ 심사 종료 |
|---|---|---|
| 필드 **추가** | 모르는 필드는 무시한다 | ✅ 가능 |
| 필드 **삭제** | 읽던 값이 사라진다 | ❌ 하지 않음 |
| 필드 **이름 변경** | 삭제와 같다 | ❌ 하지 않음 |
| 값의 **형태 변경** (숫자 → 문자열, 배열 → 객체) | 화면이 깨질 수 있다 | ❌ 하지 않음 |
| 요청 파라미터 변경 (`limit` 상한 축소 · `op` 값 변경) | 받던 결과가 달라진다 | ❌ 하지 않음 |

적용 대상은 앱이 쓰는 API 둘 — **`/api/recommend` · `/api/weather`**.
예: `recommend` 응답에서 `crowdLevel` · `stayMinutes` 를 빼는 변경은 업로드 후라면 심사용 앱을 깨뜨린다.
이 기간에 응답 구조를 바꿔야 하면, 앱 재빌드 · 재심사 일정과 함께 정한다.

## 5. 출시까지 남은 단계

```
 ① 확인 요청
    ├─ 유나: 프로토타입 버전 코드 · 아이콘 512px ─────────┐
    └─ 에린: CORS 방식 · 응답 규칙 ─────┐                 │
                                       ▼                 │
 ② 코드 정리        main 반영 · CORS 교체 · 빌드 확인        │
                                       ▼                 │
 ③ 서버 반영        PR 머지 ─▶ Vercel 자동 배포 ─▶ CORS 확인 │
                                       ▼                 │
 ④ 앱 파일          버전 코드 · 아이콘 반영 ◀────────────────┘
                    ─▶ 서명된 APK · AAB
                                       ▼
 ⑤ 테스트           에뮬레이터에서 설치 · 동작 확인
                                       ▼
 ⑥ 업로드           유나가 원스토어 콘솔에 AAB 업로드 ─▶ 심사
```

| 단계 | 담당 | 끝난 기준 |
|---|---|---|
| ① 확인 요청 | 서영 | 버전 코드 · 아이콘 · 에린 동의 받음 |
| ② 코드 정리 | 서영 | 웹 빌드 · 앱 빌드 · 타입 검사 통과 |
| ③ 서버 반영 | 서영 · 리뷰어 | 배포된 API 응답에 `Access-Control-Allow-Origin` 있음 |
| ④ 앱 파일 | 서영 | 서명된 AAB 생성 |
| ⑤ 테스트 | 서영 | 목록 · 저장 유지 · 언어 · 오프라인 안내 확인 |
| ⑥ 업로드 | 유나 | 심사 요청 완료 |

### 이번 앱 버전 범위

| 포함 | 제외 |
|---|---|
| 진단 · 조건 입력 · 추천 목록 · 저장 · 한/영 | 장소 상세 (다음 업데이트) |

앱이 쓰는 API 는 `/api/recommend` · `/api/weather` 둘이다. `/api/place/*` 는 장소 상세가 들어가는 업데이트부터 쓴다.

## 6. 백엔드 작업 시 체크

| | 할 일 |
|---|---|
| 화면에서 새 API 를 부를 때 | `fetch(apiUrl("/api/…"))` |
| 새 API 라우트를 만들 때 | 없음 — CORS 는 서버 설정에서 자동 적용 |
| `recommend` · `weather` 응답을 바꿀 때 | 업로드 ~ 심사 종료 기간엔 추가만 — 삭제 · 이름 · 형태 · 파라미터 변경 안 함 |
| `useRecommendations.ts` 를 main 과 합칠 때 | `apiUrl(…)` 이 남아 있는지 확인 |
